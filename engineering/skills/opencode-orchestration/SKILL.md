# opencode-orchestration

## 0. 元信息

```yaml
name: opencode-orchestration
version: 0.1
domain: 工程流程（AI 执行器调度编排：发现 → 派发 → 解阻 → 恢复）
trigger:
  - 搭建或维护「多工单 + AI 编码执行器」的自动调度层（supervisor/dispatcher/审批/交付环）
  - 调度排障：工单不派发、派发了没会话、executor 楔死、权限卡死、闸门冻结、双跑重复触发
  - 把 opencode 类执行器接入既有 issue 驱动流水线并要求无人值守运转
requires_tools:
  - git 托管 REST API（Gitea/GitHub：issues、labels、comments）
  - CI 触发 API（Jenkins 类：trigger / queue / build 状态）
  - opencode serve API（/session、/session/{id}/message、/permission、abort/interrupt）
  - 轻量定时器（cron：no-agent 脚本型 + agent 型各若干）
output_artifacts:
  - 工单机器指令与标记评论（dispatch:/review:/rework:/decision:）
  - 派发判重 state 文件（指令评论 id 锚点）
  - 审批审计日志与 evidence 评论
provenance: 实战于两个并行业务仓（不同技术栈、共用一套调度层）的多工单交付流水线，REQ→DES→TDD 全阶段无人值守运转
```

**与 `github-jenkins-opencode` 的分工**：那份管「流水线骨架」（评论状态机词汇、闸门 lane、Jenkins 合同、双仓契约）；本份管「调度运行时」——谁在什么节拍拉单、派发、解阻、恢复。两份配套使用，词汇以那份 §3.2 为准。

**一句话立场**：状态只存评论、派发必须幂等、阻塞走快车道、恢复保留上下文。调度层只做「感知→派发→解除→恢复」，裁决留给 CI 与人；判死宁可多等一轮，恢复宁可换会话，绝不重复造状态。

## 1. 调度拓扑：四条回路（快慢分层是第一设计）

| 回路 | 职责 | 节拍 | 类型 | 关键约束 |
|---|---|---|---|---|
| ticket-dispatcher | 指令 → 派发触发（机械转译） | 1-2 min | no-agent 脚本 | 零 LLM、判重幂等、无事零输出 |
| permission-review | executor 权限 ask 审批 | 3-5 min | no-agent 脚本 + 按需 LLM | 常态零 token；fail-safe 永不默认放行 |
| supervisor | 巡检、扫障、裁决转译、缺口建单 | 60 min 级 | agent | 唯一派发者；只裁不打字 |
| delivery-loop | 闸门验证 + 绿灯合并收口 | 15 min 级 | agent | 只读 verdict，不派发、不改码 |

**分层纪律**：latency 敏感的机械动作（轮询、触发、审批）一律 no-agent 高频轻脚本；agent 型 interval 的实测节拍是「上轮结束 + 轮次时长」（60~90min 一跳），救不了延迟——把触发放进 agent 回路是常见错误设计（指令发出后小时级才动）。

**唯一派发者原则**：实现工单只有一个派发入口（supervisor 或 dispatcher 二选一为「决定派谁」的脑子，另一个只做机械触发）。永不并行跑第二个派发者——双派发 = 双会话互踩共享 checkout（实测 A 单提交后 B 单切分支，A 的 diff 变空险些改错树）。

## 2. issue 拉取（发现层）：口径决定「有没有漏单」

### 2.1 扫描口径
- `state=open` + `ready` 标签为默认扫描面；**排除 `done/blocked/needs-info`**（`needs-info` 只有人能解除）。
- **用户提的 REQ/BUG 单与规划缺口单同权**，全部进扫描面——只盯规划单会把用户单饿死在队外。
- PR 过滤用**真值判断**（`if item.get("pull_request")`）：issue 对象恒带 `pull_request` 键（纯 issue 为 null），键存在性判断会把整个列表误判空（实测误报 open issues=0）。

### 2.2 待派发判据（评论即状态机）
- **待派发 = 最新 `review:`/`rework:` 指令比最新 `dispatch:` 标记新**（阶段流转/返工未消费）。
- **零评论的新工单永不满足自动派发条件** → 立项四件事按序落：`decision:` 拍板记录 → `ready` 标签 → 指令评论（触发锚）→ 验证派发锚点落地。「先排队」变体只落前两件。
- **终阶豁免**：`review: passed TDD` 是会话末阶（之后走 PR 收口），把它当普通推进指令会补发零产出会话（实测多起，全部中止收场）。

### 2.3 拉取层自防护
- 列表/评论拉取失败 = 跳过下轮再扫，**绝不把网络异常误判为「零工单」**（输出一行原因，但不改状态）。
- 「列表空」≠「队列空」：被 `ready` 标着但实为等人工裁决的单要具名汇报，别报「无事」。

## 3. 派发（执行层）：幂等是唯一保险

### 3.1 判重键
- **判重键 = 指令评论 id**（state 文件按 `<repo>#<n>: <指令id>` 记录已触发项）。只比 SHA 会把推进（next）误判成返工（revise）导致返工永不派发；只比时间序会重复触发。
- 全链路允许 at-least-once：重复触发被判重键免疫，每个组件都可放心重试。

### 3.2 触发纪律
- **目标 job 构建中一律跳过本轮**——很多编排 job 是 `abortPrevious` 语义，新触发会把在途派发构建整个顶掉（Superseded）。
- **顶掉 = 静默停摆陷阱**：判重锚点已写、构建被顶掉 → `dispatch:` 标记和会话都不会出现 → 锚点让派发器不再重试。故**触发后必须双验**（`dispatch:` 锚点评论 + 新 executor 会话都出现），缺一即补触发一次（安全：会话与消息在同步调用返回前已落服务端）。
- 触发成败看返回 HTTP 状态（201=入队），**触发封装常恒 exit 0**，shell 里别只看 return code。

### 3.3 派发合同（一次 run = 一个会话）
1. **先落锚点评论** `dispatch: <kind> @<sha>`（implement/next/revise）——状态机以评论为唯一事实源，锚点先落即再入安全；
2. `POST /session`：metadata 带 `issue/repo/stage/build`（审批与审计靠它定位归属），**权限表在创建时冻结进会话**（改规则不热更，只对新会话生效）；
3. `POST /session/{id}/message`：同步长调用（可达数十分钟）**必须容错 `|| true`**——超时 ≠ 无产出（实测超时被杀后会话照常完成），产出看分支/评论状态机，绝不因非零退出拖垮构建、绝不重发 prompt（防双回合）。

### 3.4 会话与工作树纪律
- **一单一一会话、不并发双会话**；实现位按队列序接派，闸门道与实现道并行互不阻塞。
- 派发提示**自包含**（executor 不知 chat 历史）：目标 + 原因、分支约定、精确文件清单（清单外不得改动）、已实测的引证（file:line，**引证先行**——缺失会让 executor 自行开 explore 子代理，实测楔死 30 分钟级）、闸门命令、命令保证退出码 0（`|| true`）、返回格式。
- **模型 pin 必须先行探针**：未知模型 id 或端点不匹配的 key 会被接受后**静默空回合**（HTTP 200、零事件、零产出）——派发前用一次性 PONG 会话验证 pin。
- 工作树显式从主干起分支；开 PR 前核 merge-base 确认「compare 仅本单提交」；叠了他单分支就 cherry-pick 本单提交重落新分支（force push 被门禁拦也别绕：换新分支名接替，旧头保档零销毁）。

## 4. 解除阻塞（unblocking）：每类阻塞一条快车道

### 4.1 权限 ask（最高频阻塞）
- 专用 3-5min no-agent 审批回路：`GET /permission` 拿 pending → 判定 → `POST /session/{sid}/permissions/{rid}` 回 `once/always/reject`；空列表零输出零 token。
- **宁松勿拒**：reject 会直接终结 executor 整个回合（模型不再被调用、零产出）。只拒真正危险操作（删文件/外传/改系统/装包/碰凭据/工作区外写）；只读探查、工作区内读写、测试构建命令族一律放行。
- 判定失败（LLM 挂/解析失败）**保持 pending 下轮重试**——fail-safe，绝不默认放行。
- **评论通道必须预置白名单**（专用发评脚本 + 审批规则显式放行）：没给合法发评途径，executor 会翻环境找凭据 → 被拒 → 回合报废。
- 治本靠**会话级权限白名单**：只读探查 + 按技术栈列测试/构建命令族全放行 + 防重定向三规则（`>` `>>` `-exec` 一律 ask）；探索类 ask 的大头用「干净的 serve 根目录（只含目标仓符号链接，ls 一眼见底）」消除。

### 4.2 question 过期楔死（裁决类阻塞）
- 判据：消息尾停在 question 工具且无 completed，而 `GET /question` 已空（请求在服务端过期，reply 404）——工具态停 running，会话永久 busy。
- 修复：`POST /session/{id}/interrupt` → `POST /session/{id}/prompt`（**body 形状是 `{"prompt":{"text":…}}`**，裸 `{"text":…}` 被拒），把拍板结论直接写进续跑 prompt，并在工单留 `decision:` 记录。

### 4.3 人工裁决解除（needs-info / blocked）
- 裁决回写四件事（缺一流程就僵死在「待裁决」）：① `decision:` 记录评论 → ② `review:`/`rework:` 指令评论（机器触发锚）→ ③ 标签翻转（用 labels 专用端点 + **GET 回读**，通用更新端点的 labels 字段常是静默 no-op）→ ④ 2~3 分钟后验证派发锚点落库，未落即补触发。
- 判 BLOCKED 前**读评论流**：标签与正文都滞后于裁决（实测裁决落档 30 分钟后标签仍是 needs-info），「有裁决评论比标签新」就不算阻塞。

### 4.4 环境阻塞（闸门冻结 / 工具链坏）
- **先修环境再触发**，顺序不能反：坏环境上重触发只烧构建分钟数。
- 修复位三件套：repair job（探测+条件重装）、只读探针 job、烟测 job（出明确 OK 信号才算康复）。
- 手动补 trigger 有重复占道风险（重复慢闸单次占道 80min 级）——优先依赖判重幂等让下一轮自动恢复；闸门解冻后**按原队序**放行，不重排不插队。

## 5. 异常恢复（recovery）：先判死，再保上下文

### 5.1 楔死判定与修复（核心口径）
- **45 分钟三无 = 卡死**：无新消息部件、无分支提交、无工单评论。三者有其一就还在干活。
- **静默不是卡死**：长 reasoning 回合 10~14 分钟属常态（reasoning 文本与 token 计数回合完成才落盘）；构建「日志持续增长」即存活。
- 修复优先级：**abort 当前回合 + 同会话续跑**（保留实读上下文）> 删失效 dispatch 锚点重建会话重派。abort 只杀回合不丢会话；abort 后会话常不自动恢复，续跑要显式发 prompt。
- **写工具家族连挂**（edit/write 停 running，同日可三发）：续跑 prompt 直接禁用 edit/write，令其用 bash 整文件读改写，并要求**里程碑增量提交**（红测试落盘即 commit）防丢现场；复发 2~3 次即 supervisor 接手实现——用户反复卡死时宁可人工介入，不无限重试 agent。

### 5.2 状态读数陷阱（误判是二次事故之源）
- **busy 会残留**：已收口会话可挂 busy 11 小时+；判实现位占用以消息尾部时间为准，勿只看 status。
- 会话消息列表**新→旧**排序（首条最新）；旧版列表可滞后 1 小时+，勿据旧读数判死活。
- **超时 exit 28 ≠ 失败**：先查分支提交和工单评论再判无产出。
- 进程/构建活着 ≠ 在干活；空回合（零部件）≠ 派发成功——核实传感器是「产出锚点」不是「进程表」。

### 5.3 判红口径（瞬态 vs 语义）
- **同签名基础设施红**（DB 超时、挂载层写坏、连接异常）判环境瞬态：原地重触发不返修，判断依据写 `decision:` 留档；用例断言失败但服务端日志显示基础设施异常的同判瞬态。
- **只有代码语义失败走 rework**；反复同签名红才升级为 CI 韧性缺口建单，不为单次瞬态建单。
- 假绿防御：「测试列出了 N 条」不等于跑绿——涉及新写测试的工单，验收必须是**实跑**这些测试的输出。

### 5.4 双跑与重复触发清理
- 定时任务可能重叠双实例，会对同一事件各自行动——动手前先读目标对象最新标记评论，已有同结论记录就跳过。
- 已误触发的补救：abort 在跑构建 + 取消排队项（两者都要 crumb + cookie 会话，裸 POST 403）；合并/推送类副作用操作后**回读验证**再报成功。

### 5.5 恢复后验证闭环
- 会话复活判据：status 变 busy + 消息列表出现新 assistant 条目 + 分支/评论推进，三项至少一项新读数；
- 任何修复动作（补触发、续跑、标签翻转）都要留一个可回读的锚点，下轮巡检顺带核销。

## 6. 成功经验（照做）

1. **快慢分层**：机械动作 no-agent 分钟级，判断动作 agent 小时级——延迟从小时压到分钟全靠这一条。
2. **评论即状态机 + 判重幂等**：全部调度状态在工单评论 + state 锚点文件，一切自动触发可重复、可重入、可审计。
3. **fire-and-forget + 双验**：触发不等执行；触发后验锚点，派发后验会话，两头都回读。
4. **预授权矩阵**：把决策分级（工程类自主拍板 + `decision:` 留一行依据；产品/架构/行为变更/不可逆四类升级），否则小事堆积等人、队列饿死。
5. **静默输出纪律**：无事只回一个字——watchdog 语义（空输出=不投递）让高频回路零噪音，噪音会淹没真告警。
6. **宁松勿拒的审批**：一次误拒报废整个回合，比一次误放代价高一个量级。
7. **45 分钟三无判死**：唯一的卡死口径，防止在长 reasoning 回合上误杀、也防止在楔死会话上空等。
8. **恢复保上下文**：abort+续跑优先于重派新会话，重派最后才用（丢调研上下文 = 重复烧 token 还可能改错）。
9. **一单一一会话**：共享 checkout 上并行会话互踩是实测事故，队列化是免费的正确性。
10. **supervisor 只裁不打字**：监督者的杠杆是验证与派发，不是亲自写码——但 agent 反复卡死时人工/监督者直接接手，不死磕。

## 7. 教训表（症状 → 根因 → 规则）

| # | 症状 | 根因 | 规则 |
|---|---|---|---|
| O1 | 指令发出小时级才动 | 触发/轮询放进 agent 型 cron | 机械动作 no-agent 1-2min（§1） |
| O2 | 派发后既无标记也无会话 | 锚点先写、构建被 abortPrevious 顶掉 | 构建中跳过 + 触发后双验（§3.2） |
| O3 | 同指令反复派发/永不派发 | 判重只比 SHA 或只比时间 | 判重键=指令评论 id（§3.1） |
| O4 | 零评论新工单永远不动 | 判据是「指令比标记新」 | 立项四件事（§2.2） |
| O5 | TDD 后补发零产出会话 | 终阶指令被当推进 | 终阶豁免（§2.2） |
| O6 | executor 回合秒收工零产出 | 权限 reject 终结整个回合 | 宁松勿拒 + 评论通道预置（§4.1） |
| O7 | 会话 busy 永久、形似卡死 | question 过期 / 写工具挂 running | 45min 三无判死 + interrupt/prompt（§4.2/§5.1） |
| O8 | 裁决后流程仍报「待裁决」 | 裁决没回写成机器可读状态 | 裁决回写四件事（§4.3） |
| O9 | 「请求成功」但状态没变 | 触发封装恒 exit 0 / 标签接口静默 no-op | 写后回读验证（§3.2/§4.3） |
| O10 | 重复触发慢闸、占道 80min 级 | 双实例双跑 / 手动补触发 | 先读最新标记、只留一个派发入口（§5.4/§1） |
| O11 | 模型 200 返回、零产出 | pin 了未知模型/错端点，静默空回合 | pin 前 PONG 探针（§3.4） |
| O12 | 超时被杀被判「无产出」 | 同步调用超时 ≠ 任务失败 | 超时容错 + 状态机核产（§3.3） |

## 8. 新项目落地清单

1. **P0 一条闭环**：一个工单仓库 + 一条 no-agent dispatcher（判重键=指令评论 id）+ 一个 executor（权限白名单按栈补命令族）+ 立项四件事。
2. **回路按序补齐**：审批快车道（宁松勿拒 + fail-safe）→ supervisor 巡检（45min 三无判死 + 裁决回写四件事）→ 交付环（两绿合并 + 回读验证）。
3. **每回路一个传感器**：派发看锚点+会话、执行看分支/评论、审批看审计日志、合并看回读——没有可回读锚点的环节就是开环。
4. **红线四条**（落地就要有，不能后补）：状态只存评论；判重键含指令身份；触发后双验；reject 默认禁止。
